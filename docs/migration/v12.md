## Node.js Support

The minimum supported Node.js version is now `^22.23.5 || ^24.22.3 || >=26.13.1`: the security releases of each supported line at the time of this release. Node.js 20, 23 and 25 are end-of-life and no longer supported, and earlier patch releases of 22, 24 and 26 miss security fixes. Upgrade Node.js before upgrading `listr2`.

## Breaking Changes

Apart from three changes, these change what the _DefaultRenderer_ prints. No code changes are required for them, but snapshot tests of the output and anything parsing it may need updating. The three others are the removal of `DefaultRenderer.create()`; the input lock, so a task that reads the terminal itself, such as a child process spawned with `stdio: 'inherit'`, needs the renderer option `lockInput: false`; and option values that used to hang or render nothing, which now throw.

### Finished tasks are persisted while the list runs

The _DefaultRenderer_ no longer redraws the whole task list on every update and prints it again at the end. Tasks that will not change anymore are written once, above a live region that holds everything still running, and scroll into the scrollback of the terminal. Long task lists no longer lose their top, and duplicated lines no longer pile up when the terminal is resized; see [Resizing the Terminal](../renderer/default.md#resizing-the-terminal) for what a resize can still leave behind. See [How Updates Are Rendered](../renderer/default.md#how-updates-are-rendered).

With the default options, the final output is the same as before, except for the changes below.

### Concurrent lists are printed in the order their tasks finish

Tasks of a list with the `concurrent` option are persisted as soon as they finish, so the final output shows them in the order they finished instead of the order they were declared in.

### `collapseSubtasks: false` prints the final status line after the subtasks

A task with `collapseSubtasks: false` persists its subtasks as they finish. Its title is persisted with its subtasks still running, and its final status line is printed after its subtasks. The two lines are drawn as the header and the footer of a bracket, described below, so they read as one group, and once it finished, the footer shows only its status. See [When Tasks Are Persisted](../renderer/default.md#when-tasks-are-persisted).

```text
// before
✔ Running migrations
  ✔ Running migration 001.
  ✔ Running migration 002.
  ✔ Running migration 003.

// after, while it runs
┌ Running migrations
│ ✔ Running migration 001.
│ ✔ Running migration 002.
│ ⠋ Running migration 003.
└ ❯

// after, once it finished
┌ Running migrations
│ ✔ Running migration 001.
│ ✔ Running migration 002.
│ ✔ Running migration 003.
└ ✔
```

### Expanded subtasks are drawn as a bracket

Every task that shows its subtasks under its title is drawn as a bracket: a header with its title, a dimmed `│` in the first column of the indentation of its subtasks, and a footer with its status. That covers a task whose subtasks collapse while it runs, a task that stays expanded because a subtask failed, rolled back, or was cancelled, a task that retries, and every task with `collapseSubtasks: false`. A task whose subtasks collapse and finish without a problem is still persisted as a single line. While a task runs, its footer in the live region shows the icon of the task: `❯` while it runs, or the spinner of a retry followed by `[RETRY:n]` while it retries, and its title only once the header can no longer be on the screen. Once the task finished, its footer shows only its final icon, a red `✖` when it failed, followed by its timer when the `timer` renderer option of the task is on. While it runs and once it finished, the footer also shows the title when the title changed after the header was persisted. A footer with only its icon ends on a space, since some terminals, such as kitty, draw a symbol that ends the line narrower than one with a space after it. The header and the footer take the column of the icon of the task, and the connector the place of a space, so the width of every line stays the same.

The glyphs are `┌`, `│` and `└`, or `.`, `|` and `` ` `` when the terminal does not support unicode, and can be changed through the `icon` and `color` renderer options with the `ListrDefaultRendererLogLevels.CONNECTOR_START`, `CONNECTOR` and `CONNECTOR_END` keys. Tasks without a title, and every task when `indentation` is `0`, draw no bracket. Set the renderer option `markIndentation` to `false` to draw no bracket: a task with `collapseSubtasks: false` then persists its title with the `❯` icon before its subtasks, and its closing line, with its title and timer, after them. See [When Tasks Are Persisted](../renderer/default.md#when-tasks-are-persisted).

```text
// before
⚠ Validating config
  ✔ Validating package.json.
  ✖ compilerOptions.target is missing.

// after
┌ Validating config
│ ✔ Validating package.json.
│ ✖ compilerOptions.target is missing.
└ ⚠
```

### Lists taller than the terminal are summarized while they run

While the live region is taller than the terminal, the finished subtasks of a task whose subtasks collapse that do not fit are shown as a single `↑ N` line that counts them until the task closes, and then the tasks that have not started yet and do not fit as a single `… N` line. The summary lines have their own icons, `↑` and `…`, or `^` and `+` when the terminal does not support unicode, which the `ListrDefaultRendererLogLevels.SUMMARY_COMPLETED` and `SUMMARY_WAITING` keys of the `icon` and `color` renderer options change. The final output is unchanged, since every task is persisted in full once it finishes. See [Taller Than the Terminal](../renderer/default.md#taller-than-the-terminal).

### Output written to `stdout` and `stderr` appears as it arrives

Anything written to `process.stdout` or `process.stderr` while the _DefaultRenderer_ runs is written above the task list as it arrives, instead of after the task list once the run has finished.

### Keyboard input is not echoed while the tasks run

The _DefaultRenderer_ turns off the echo of the terminal with `stty -echo` while the tasks run, so pressing Enter or typing does not move the task list. What is typed is not shown, and reaches the shell after the run. `Ctrl+C`, `Ctrl+\`, `Ctrl+Z` and prompts work as before. Set the renderer option `lockInput` to `false` when a task reads the terminal input itself, such as a child process spawned with `stdio: 'inherit'`. See [Keyboard Input](../renderer/default.md#keyboard-input).

### `DefaultRenderer.create()` is removed

The public `create()` method of the _DefaultRenderer_, which rendered the whole task list into a string, is removed. The renderer itself no longer used it, and it could not show the tasks that had already been persisted. A custom renderer that extends the _DefaultRenderer_ and calls `create()` has to render the task list itself.

### Invalid option values throw

Option values that made a list hang or render nothing now throw a `RangeError` that names the option and the value. It is thrown when the list or the task is created, before anything renders, so a subtask list created with such a value fails its parent task.

- `concurrent`: `0`, a negative number or `NaN`. No task ever started, so `run()` never settled. `true`, `false`, `Infinity` and positive numbers, fractions included, work as before.
- `retry` and `retry.tries`: a fraction greater than `0`. The task kept retrying past its last try and then passed. `0`, a negative number and `NaN` still mean no retries.
- The _DefaultRenderer_ options `indentation` when negative or `NaN`, `formatOutput` when it is neither `truncate` nor `wrap`, and `outputBar` and `bottomBar` when negative or `NaN`.

## Fixes

- `Task.isClosed()`, as seen by renderers, returns `true` once a task has finished, including tasks skipped through the `skip` option. It was never set before.
- When a run is interrupted, the subtasks that never started are marked as cancelled before their parent finishes, instead of being left as waiting.
